# Приложение для учета личных финансов

## Описание проекта

Данный проект представляет собой консольное приложение для управления личными финансами.

Приложение позволяет пользователю создавать банковские счета, определять категории доходов и расходов, фиксировать финансовые операции, а также выполнять импорт/экспорт данных и получать аналитические отчеты.

**Технологический стек:**
*   **Язык:** Java 21
*   **Фреймворк:** Spring Boot 3
*   **Система сборки:** Gradle
*   **Взаимодействие с пользователем:** Spring Shell
*   **База данных:** H2 (встраиваемая, in-memory)
*   **Работа с данными:** Spring Data JPA

---

### Основная функциональность

*   **Управление счетами:** Создание, удаление и просмотр списка банковских счетов.
*   **Управление категориями:** Создание, обновление и просмотр категорий доходов и расходов.
*   **Управление операциями:** Добавление финансовых операций (доходов/расходов) с привязкой к счету и категории.
*   **Импорт данных:** Загрузка всех данных (счета, категории, операции) из файлов формата `JSON` и `YAML`. При импорте старые данные полностью заменяются.
*   **Экспорт данных:** Выгрузка всех текущих данных в формат `JSON`.
*   **Статистика:** Автоматическое измерение и логирование времени выполнения пользовательских команд.
*   **Аналитика:** Формирование сводного отчета по доходам, расходам и их разнице за указанный период с группировкой по категориям.

### Инструкция по запуску

**Требования:**
*   JDK (Java Development Kit) версии 21 или выше.
*   Gradle (обычно устанавливается автоматически через `gradlew` wrapper).

**1. Сборка проекта:**
Откройте терминал в корневой папке проекта и выполните команду:
```bash
# Для Windows
./gradlew.bat build

# Для macOS/Linux
./gradlew build
```
Эта команда скачает все зависимости и соберет исполняемый `.jar` файл.

**2. Запуск приложения:**
После успешной сборки запустите приложение командой:
```bash
java -jar build/libs/finance-tracker-0.0.1-SNAPSHOT.jar
```
Вы увидите стартовый баннер Spring Boot и приглашение к вводу команд `shell:>`.

### Пример использования

1.  **Создайте банковский счет:**
    ```shell
    shell:> create-account --name "Карта Альфа-Банка" --balance 10000
    > Счет успешно создан! ID: a1b2c3d4-....
    ```
    *(скопируйте полученный ID)*

2.  **Создайте категорию расходов:**
    ```shell
    shell:> create-category --name "Рестораны и кафе" --type EXPENSE
    > Категория успешно создана! ID: e5f6g7h8-...
    ```
    *(скопируйте полученный ID)*

3.  **Добавьте операцию расхода (используя полученные ID):**
    ```shell
    shell:> add-operation --account-id <ID_счета> --category-id <ID_категории> --amount 450 --type EXPENSE
    ```

4.  **Просмотрите список счетов и убедитесь, что баланс изменился:**
    ```shell
    shell:> list-accounts
    ```

5.  **Получите аналитический отчет за текущий месяц:**
    ```shell
    shell:> run-analytics
    ```
6.  **Для просмотра всех доступных команд введите `help`**

### Архитектура и принципы проектирования

Проект построен на основе **многослойной архитектуры**, что позволяет разделить зоны ответственности и обеспечить слабую связанность (Low Coupling) и высокую связность (High Cohesion).

*   **`domain` (Доменный слой):** Ядро приложения. Содержит модели (`BankAccount`, `Category`), интерфейсы репозиториев, фабрики и посетителей. Не зависит от других слоев.
*   **`application` (Прикладной слой):** Оркестрирует бизнес-логику. Содержит фасады (`FinanceFacade`), DTO и команды. Выступает посредником между слоем представления и доменным слоем.
*   **`infrastructure` (Инфраструктурный слой):** Содержит технические детали реализации: работа с БД, парсеры файлов, декораторы. Реализует интерфейсы, определенные в доменном слое.
*   **`presentation` (Слой представления):** Отвечает за взаимодействие с пользователем. В данном проекте это консольный интерфейс на Spring Shell.

#### Принципы SOLID

*   **S (Single Responsibility Principle):** Каждый класс имеет одну зону ответственности. `OperationRepository` отвечает только за доступ к данным операций, `AnalyticsFacade` — только за формирование отчетов, `JsonDataImporter` — только за парсинг JSON.
*   **O (Open/Closed Principle):** Система открыта для расширения, но закрыта для модификации.
    *   **Декоратор:** Добавлено логирование времени (`TimingCommandDecorator`) без изменения исходного кода команд.
    *   **Шаблонный метод:** Архитектура позволяет добавить импорт из нового формата (например, XML) путем создания нового класса-наследника `AbstractDataImporter` без изменения существующей логики.
*   **L (Liskov Substitution Principle):** Объекты в программе могут быть заменены их наследниками без изменения свойств программы. Для обеспечения взаимозаменяемости реализаций используются интерфейсы (`Command`, `DataVisitor`).
*   **I (Interface Segregation Principle):** Созданы специфичные интерфейсы (`BankAccountRepository`, `CategoryRepository`) вместо одного большого "God-репозитория".
*   **D (Dependency Inversion Principle):** Модули верхних уровней не зависят от модулей нижних уровней. Оба зависят от абстракций. `FinanceFacade` (прикладной слой) зависит от интерфейсов `Repository` (доменный слой), а не от их конкретных реализаций (инфраструктурный слой). Зависимости внедряются через DI-контейнер Spring.

#### Принципы GRASP

*   **High Cohesion / Low Coupling:** Обеспечиваются многослойной архитектурой и принципом инверсии зависимостей.
*   **Information Expert:** Логика размещена там, где есть необходимые для нее данные. Например, логика валидации операции находится в `OperationFactory`.

### Реализованные паттерны проектирования (GoF)

#### Порождающие паттерны

*   **Фабричный метод (Factory Method):**
    *   **Проблема:** Централизовать создание объектов `Operation` и добавить им бизнес-валидацию (например, сумма операции не может быть отрицательной).
    *   **Реализация:** Класс `OperationFactory` (`com.hse.financetracker.domain.factory`) инкапсулирует логику создания и валидации операций. `FinanceFacade` делегирует создание объектов этой фабрике вместо использования оператора `new`.

#### Структурные паттерны

*   **Фасад (Facade):**
    *   **Проблема:** Упростить взаимодействие с подсистемами приложения.
    *   **Реализация:**
        *   `FinanceFacade`: Единая точка входа для основных CRUD-операций.
        *   `AnalyticsFacade`: Предоставляет простой метод для генерации сложного отчета.
        *   `DataManagementFacade`: Скрывает логику выбора нужного импортера/экспортера.

*   **Декоратор (Decorator):**
    *   **Проблема:** Динамически добавить новую функциональность (измерение времени) к существующим операциям, не изменяя их код.
    *   **Реализация:** `TimingCommandDecorator` "оборачивает" любой объект `Command`, измеряет время его выполнения и затем вызывает оригинальный метод `execute()`.

#### Поведенческие паттерны

*   **Команда (Command):**
    *   **Проблема:** Инкапсулировать запрос или действие как объект, что позволяет параметризовать клиенты с разными запросами, ставить запросы в очередь или логировать их, а также поддерживать отмену операций.
    *   **Реализация:** Интерфейс `Command<T>` и его реализации (`ListAccountsCommand` и др.) превращают каждое действие пользователя в отдельный объект. Это позволило легко применить паттерн Декоратор.

*   **Шаблонный метод (Template Method):**
    *   **Проблема:** Определить общий алгоритм импорта данных, оставив реализацию специфичных шагов (парсинг конкретного формата) подклассам.
    *   **Реализация:** Абстрактный класс `AbstractDataImporter` определяет общий метод `importFromFile()`, который вызывает абстрактный метод `parseData()`, реализованный в наследниках (`JsonDataImporter`, `YamlDataImporter`).

*   **Посетитель (Visitor):**
    *   **Проблема:** Добавить новую операцию (экспорт в JSON) к существующим классам доменной модели (`BankAccount`, `Category`, `Operation`), не изменяя их код.
    *   **Реализация:** Доменные модели реализуют интерфейс `Visitable`. `JsonDataVisitor` реализует интерфейс `DataVisitor` и содержит логику обхода объектов и их преобразования в DTO для последующей сериализации в JSON. Это позволяет легко добавить `YamlDataVisitor` или `CsvDataVisitor` в будущем.
